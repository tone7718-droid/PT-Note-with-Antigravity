# 저장·백업 안전성 변경

## 적용 범위

- 동일 origin·브라우저 프로필의 여러 탭에서 데이터 읽기/수정/암호화/쓰기를 Web Locks로 직렬화합니다. 키 생성도 별도 공용 잠금으로 보호합니다.
- 편집 화면에서 읽은 savedAt과 저장 직전 기록의 savedAt이 다르면 저장을 거부합니다. 다른 탭의 기록 변경은 목록에 반영하되 작성 중인 폼은 유지합니다. 충돌 시 입력을 복사해 보관하고 다른 기록을 선택했다가 다시 여세요.
- Web Locks가 없는 브라우저/WebView에서는 안전하지 않은 대체 저장을 하지 않고 오류를 표시합니다. HTTPS/localhost와 최신 WebView가 필요합니다. 기존에 열려 있던 구버전 탭은 모두 닫고 새 버전으로 다시 여세요.
- 복호화 실패·키 분실·손상된 기록은 빈 목록으로 처리하지 않습니다. 원본 저장 키를 보존하고 변경을 중단합니다.
- 삭제·수정·가져오기·복원 직전 자동 백업이 실패하면 해당 기록 변경을 중단합니다. 최근 최대 5개를 보관하며 용량 부족 시 오래된 백업부터 줄입니다. 브라우저 저장소를 지우면 로컬 백업도 사라지므로 별도 파일 백업이 필요합니다.
- 자동 복원은 현재 노트 전체를 선택한 시점으로 교체합니다. 복원 직전 상태도 저장하고, 현재 치료사 계정과 비밀번호는 유지합니다.
- 세 앱의 평문/암호화 백업을 같은 검증 경로로 가져옵니다. 정상 항목 추가 수, 중복 제외 수, 잘못된 항목 제외 수를 표시합니다. 기존 노트 ID는 덮어쓰지 않습니다.
- 다른 앱에서 생성된 환자 ID는 차트번호 또는 차트번호가 없는 경우 이름+생년월일로 기존 환자와 연결합니다. 서로 다른 병원의 차트번호는 동일 환자임을 뜻하지 않으므로 병원 간 백업 병합 용도로 사용하지 마세요.
- 비밀번호 해시가 없는 가져온 계정은 로그인 잠금 상태이며 관리자의 비밀번호 재설정이 필요합니다. 암호화 백업의 해시 포함 여부는 원본 앱의 내보내기 정책을 따릅니다. 기존 관리자 계정은 대체하지 않습니다.
- 노트와 계정의 일괄 가져오기는 복구 저널을 먼저 저장합니다. 쓰기 실패 시 양쪽 저장소를 되돌리고, 중단된 작업은 다음 접근에서 복구합니다. 저널의 노트 사본도 암호문입니다.

## 병원 내 다중 사용자로 확장할 때

현재 저장소는 여전히 해당 기기의 localStorage입니다. 이번 잠금은 다른 PC·프로필·origin 사이의 동기화나 서버 권한 통제가 아닙니다. 후속 단계에는 병원 식별자, 서버 인증·권한, 병원별 데이터 격리, DB 트랜잭션과 기록 버전, 작성·수정 감사 이력, 서버 백업·복구가 필요합니다. 실제 환자 데이터를 사용하기 전에 별도 배포·운영 검증이 필요합니다.

## 검증

`npm test`, `npx tsc --noEmit`, `npm run lint`, `npm run build`로 확인합니다. storageSafety.test.ts는 동시 저장/삭제, 오래된 편집 거부, 키 분실, 백업 용량 부족, 부분 가져오기 롤백, 중단 복구, 평문/암호화 교환 및 실제 내용 복원을 검사합니다. 테스트용 Web Locks 모형은 production 코드의 대체 잠금이 아닙니다.

이번 검증: 자동 테스트 40개(실제 세 앱의 내보내기 파일 6개 교차 가져오기 포함), TypeScript, ESLint 및 Next.js 프로덕션 빌드 통과. Progress의 빌드는 실행 환경 CA를 사용하기 위해 `NEXT_TURBOPACK_EXPERIMENTAL_USE_SYSTEM_TLS_CERTS=1`을 지정했습니다. 브라우저 설치가 인증서/다운로드 연결 오류로 실패하여 실제 화면 및 네이티브 패키지 실행은 이번 환경에서 검증하지 못했습니다.
